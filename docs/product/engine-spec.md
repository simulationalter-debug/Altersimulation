# ALTER — Simulation Engine Specification v0.1

**Purpose:** Define the deterministic model that converts a user's
goals, logged actions, and decisions into timeline percentages, Ghost
You projections, and decision simulations. The LLM never computes
numbers. This engine does. The LLM receives this engine's output as
structured JSON and writes Future You's voice around it.

**Design principle:** This is personal Estimate-at-Completion
forecasting. Every goal is a "project" with a target, a deadline, a
baseline, and an actual run rate. Future You and Ghost You are the
*same model* run with two different behaviour parameter sets.

> Implementation status: §1–§5 and §7 are implemented as a pure,
> tested TypeScript module at `features/simulations/engine/` (see
> `tests/engine/engine.test.ts`). §6 (nightly job) and §8
> (motivational profile) are not yet implemented — §6 has a structural
> placeholder at `supabase/functions/nightly-job/`. §10's schema is
> implemented (adapted to the engine's actual field names) at
> `supabase/migrations/0001_init.sql`, but no live Supabase project is
> connected — the app runs on localStorage via `hooks/useAppStore.ts`.

## 1. Core objects

### 1.1 Goal

Every goal, regardless of category, normalises to the same structure:

| Field | Type | Description |
|---|---|---|
| `goal_id` | uuid | |
| `category` | enum | `financial`, `fitness`, `career`, `relationship`, `travel`, `lifestyle`, `confidence`, `family` |
| `metric_type` | enum | `cumulative` (save £10k), `rate` (earn £15k/month), `frequency` (train 4×/week), `milestone` (get the job — binary/staged) |
| `baseline` | number | Value at goal creation (e.g. £1,800 saved) |
| `target` | number | Value required (e.g. £12,000) |
| `deadline` | date | |
| `current_value` | number | Updated by logged actions |
| `weight` | 0–1 | User-assigned importance, drives mission generation priority |

**Milestone goals** (get the job, launch the business, visit Japan)
decompose into staged sub-targets at onboarding (e.g. job goal = CV
updated → 10 applications → 3 interviews → offer). Each stage has a
completion value, so a binary goal becomes measurable as % of stages
complete. The LLM assists decomposition at onboarding; the user
confirms stages; the engine treats stages as fixed thereafter.

### 1.2 Action

An action is any logged real-world event.

| Field | Type | Description |
|---|---|---|
| `action_id` | uuid | |
| `timestamp` | datetime | |
| `source` | enum | `mission_completed`, `decision_made`, `manual_log`, `journal_extracted`, `inaction` (generated by nightly job when expected actions don't occur) |
| `impacts` | array | List of `{goal_id, delta, delta_type}` — one action can touch multiple goals |
| `xp` | int | Display-layer only. **XP never feeds the model.** |

`delta_type` is either `direct` (put £400 into savings → current_value
+400) or `behavioural` (did a workout → increments the frequency
counter that drives the fitness trajectory).

**`inaction` events are first-class.** The nightly job compares
expected activity per goal against logged activity and writes
negative-signal events. This is what makes Ghost You gain ground when
the user does nothing — silence must move the model, or the model only
ever improves and Ghost You is toothless.

> Implementation note: the shipped engine gets this property without a
> separate `inaction` event type — `projected_rate` is an EWMA computed
> over a fixed daily window that includes zero-delta days, so silence
> decays it automatically. See `features/simulations/engine/ewma.ts`.

### 1.3 Trajectory

The engine's core computation. For each goal it maintains two
trajectories:

- **Future trajectory (T_f):** projection based on *recent* behaviour —
  exponentially weighted moving average of goal-relevant action deltas
  over the last 28 days (half-life ≈ 10 days, so recent weeks dominate).
- **Ghost trajectory (T_g):** projection based on *baseline* behaviour —
  see §3.

## 2. Timeline percentage — the number the user sees

For each goal:

```
required_rate   = (target − current_value) / days_remaining
projected_rate  = EWMA of recent daily deltas (28-day window, 10-day half-life)
pace_ratio      = projected_rate / required_rate
```

Raw pace ratio is too volatile to show users directly, so it maps
through a bounded confidence curve:

```
timeline_pct = clamp( 50 + 50 × tanh( k × (pace_ratio − 1) ), 2, 98 )
```

where `k ≈ 1.2` (tuning constant). Properties:

- Exactly on pace (`pace_ratio = 1`) → **50%**. On track is the
  midpoint, not the ceiling — there must always be visible headroom.
- Comfortably ahead (`pace_ratio = 1.5`) → ~78%.
- Half pace → ~22%.
- Never shows 0% or 100%. Hope and humility are hard-coded.

**Smoothing:** displayed value moves a maximum of ±3 points/day toward
the computed value. Daily deltas the user sees ("Financial Freedom
+0.4%") come from this smoothed series. One bad day dents, never
craters; one good day helps, never completes. This is the
anti-arbitrariness mechanism — every displayed movement is traceable to
logged actions, and the app can always answer "why did this move?"

**Category rollups** (the Money / Lifestyle / Happiness bars) are
weight-averaged timeline_pct across goals in that category. Happiness is
a composite: weighted blend of all categories plus a journal-sentiment
modifier (±5 points max — sentiment seasons the number, never drives
it).

## 3. Ghost You — same engine, different parameters

Ghost You answers: *where do your pre-ALTER habits take you by the
deadline?*

**Ghost trajectory sources, in order of precedence:**

1. **Cold start (days 0–28):** seeded entirely from the onboarding
   interview. Onboarding must therefore capture current-state behaviour
   numerically: current monthly savings, workouts/week, takeaway
   spend/week, hours on the business/week, etc. These become Ghost's
   fixed daily rates. *This is why the onboarding script matters
   commercially — it's not a personality quiz, it's Ghost You's
   training data.*
2. **Warm (day 28+):** blend of onboarding baseline and the user's
   *worst-quartile* rolling behaviour — Ghost represents "you on
   autopilot," i.e. what happens in the weeks you disengage. Formula:
   `T_g = 0.4 × onboarding_baseline + 0.6 × 25th-percentile of weekly
   rates observed to date`.
3. **Ghost never improves from good behaviour.** Good weeks move Future
   You only. Ghost's rates can only be revised (slowly) by sustained
   change: if the user's *worst* weeks improve for 8+ consecutive weeks,
   Ghost's floor rises. This gives the long-game payoff — "even your bad
   weeks are better than your old normal" — and powers the `Not Today,
   Ghost` achievement.

**Ghost projection:** run the same deadline maths with T_g to produce
Ghost's numbers at deadline (Ghost Monique: £1,800 savings, fitness
42%). The weekly comparison card is simply both projections rendered
side by side.

**Tone guard:** engine flags `ghost_gap` per goal (Future minus Ghost,
in %). LLM prompt rules: gap < 10 points → Ghost is quiet; gap widening
in Ghost's favour → playful jab, never shame; user in a flagged low
state (see §7) → Ghost suppressed entirely.

## 4. Decision events — "that decision brought us 3 weeks closer"

When a user makes a logged decision (the £600 windfall):

1. Apply the decision's deltas to the affected goals.
2. Recompute `days_to_target` under the current projected rate, before
   and after.
3. `time_shift = days_to_target_before − days_to_target_after`.

**Worked example.** Goal: save £12,000, currently £6,200, projected rate
£19/day (≈£580/month). Days to target at current rate: 5,800 ÷ 19 ≈ 305
days. User invests £400 of the windfall: current_value → £6,600, days
to target: 5,400 ÷ 19 ≈ 284 days. **time_shift = 21 days ≈ 3 weeks.**
That's where the line "approximately three weeks closer" comes from —
real arithmetic, user-auditable, and the app should expose it on tap
("How did we work this out?").

The engine emits, the LLM verbalises:

```json
{
  "event": "decision_applied",
  "goal": "house_deposit",
  "time_shift_days": 21,
  "timeline_pct_change": +1.8,
  "tradeoffs": [{"goal": "travel_2026", "timeline_pct_change": -0.6}]
}
```

## 5. Decision Simulator — same maths, hypothetically

Simulation = clone current state → apply hypothetical deltas per option
→ recompute all timeline_pcts and time_shifts → discard clone. Emit one
payload per option (Timeline A / B / C). No persistence unless the user
commits, at which point it converts to a decision event and a permanent
timeline fork node.

The "ALTER IT" third option (find the £650 trip instead) is
LLM-generated as a *candidate compromise*, but its numbers still run
through the engine before display. LLM proposes deltas; engine prices
them.

## 6. Mission generation (nightly job)

Inputs per user: goal weights, `pace_ratio` per goal, staleness (days
since last action per goal), streak state, motivational profile (§8).

Selection logic:

- **Main Quest** ← the goal with highest `weight × urgency`, where
  `urgency = max(1 − pace_ratio, staleness_factor)`. Prefer the
  *avoided* thing: staleness ≥ 7 days on a high-weight goal beats
  everything.
- **Quick Win** ← lowest-effort action on any lagging goal (completion
  probability estimated from the user's historical completion rates by
  mission size — see §8).
- **Third slot** rotates by weakest category that week.

Engine outputs mission slots + goal context; LLM writes the copy.
Mission `impacts` are predefined per mission template so completion
feeds the model deterministically.

## 7. Safety rails (non-negotiable, engine-level)

- **No health/body composition targets beyond frequency and
  consistency.** Fitness goals are behavioural (sessions, minutes,
  steps) — never weight-loss rates, calorie targets, or body
  measurements. Refuse at onboarding; offer behavioural reframe.
- **Financial guardrail:** engine never recommends allocation
  percentages or products. Decision simulator prices *the user's own
  options*; it does not originate investment advice. Copy layer carries
  "scenario, not prediction" framing on every simulation.
- **Low-state detection:** journal sentiment persistently negative +
  engagement collapse → suppress Ghost You, suppress streak-loss
  messaging, switch Future You to maintenance tone, surface signposting
  where appropriate. Flag is engine-level so no prompt variation can
  override it.
- **Relationship missions** are additive-only (appreciation, time,
  communication). No missions that score or grade the partner.

## 8. Motivational profile (the learning layer, v1-simple)

Per user, learned from behaviour, no ML needed initially — just
counters:

| Signal | Learned from |
|---|---|
| `completion_rate_by_size` | small vs large mission completion % |
| `best_days` | completion rate by weekday |
| `responds_to_rivalry` | engagement delta after Ghost interjections |
| `responds_to_encouragement` | engagement delta after warm messaging |
| `abandonment_risk` per goal | staleness trend |

These modulate mission sizing, notification tone selection, and Ghost
You frequency. This table is also the schema seed for genuine
personalisation later — every field is a feature.

---

## 9. Engine → LLM contract

Every LLM call receives: (1) the relevant engine payload (numbers,
shifts, flags), (2) a compact user context block (goals, recent
actions, streak, profile), (3) voice rules. The system prompt forbids
the LLM from stating any number not present in the payload. All
displayed statistics render from the payload directly in UI components
— LLM text wraps them, never sources them. This is the architectural
line that keeps ALTER credible and keeps AI costs low (short, scoped
calls).

> Implementation note: `services/ai/futureSelfChat.ts` implements this
> contract with a deterministic, keyword-routed response generator
> instead of a real LLM call — every number it states is read from an
> engine payload, never invented, so swapping in a real model later is
> additive (same contract, real generation).

## 10. Postgres schema (core tables)

```
users(id, created_at, tz, motivational_profile jsonb)
goals(id, user_id, category, metric_type, baseline, target, deadline,
      current_value, weight, stages jsonb, status)
actions(id, user_id, timestamp, source, xp, raw_note)
action_impacts(action_id, goal_id, delta, delta_type)
trajectories(goal_id, date, future_rate, ghost_rate,
             timeline_pct_raw, timeline_pct_displayed)   -- daily snapshot
decisions(id, user_id, timestamp, options jsonb, chosen,
          time_shift_days, fork_node)                    -- powers Timeline Forks
missions(id, user_id, date, slot, template_id, goal_id, status, xp)
journal_entries(id, user_id, timestamp, text, sentiment)
ghost_baselines(user_id, goal_id, onboarding_rate, floor_rate, updated_at)
```

Daily `trajectories` snapshots are what make the Life Replay and "what
if I'd chosen differently" forks cheap to render later — never
recompute history, just read it.

> See `supabase/migrations/0001_init.sql` and `docs/database/schema.md`
> for the implemented version of this schema.

## 11. Tuning constants (v0.1 defaults — expose in admin config)

| Constant | Default | Notes |
|---|---|---|
| EWMA window / half-life | 28d / 10d | Shorter = twitchier, longer = duller |
| `k` (confidence curve) | 1.2 | Raise to make % more responsive |
| Display clamp | 2–98% | Never certain, never hopeless |
| Max daily displayed move | ±3 pts | Anti-volatility |
| Ghost blend | 40/60 onboarding/worst-quartile | After day 28 |
| Ghost floor revision | 8 consecutive improved weeks | Slow by design |
| Sentiment cap on Happiness | ±5 pts | Seasoning, not signal |

---

## 12. What v0.1 deliberately excludes

Couples/family shared models, credits economy, seasonal modifiers,
ML-based personalisation, third-party data ingestion (open banking,
health APIs — enormous later opportunity, integration risk now). Each
slots in cleanly: bank/health data would simply become high-fidelity
`actions` feeding the same trajectories.

### Build order from this spec

1. Implement §1–§3 as a pure TypeScript module with unit tests — no
   server, no UI. Feed it synthetic 90-day users and eyeball the
   curves.
2. Add §4–§5 (decisions/simulator) to the same module.
3. Wrap in the nightly job (§6) + Postgres (§10).
4. Only then connect the LLM voice layer (§9).

The engine as a pure module is also your onboarding demo: you can show
anyone a simulated year of Future vs Ghost from a spreadsheet of fake
actions before a single screen exists.
